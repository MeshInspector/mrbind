# Generating Python bindings over the C bindings

This is an alternative to the [pybind11-based Python bindings](/docs/generating_python.md): a CPython extension module that calls our C bindings, like the C#, Rust, Java and JavaScript backends do. It aims to produce the **same Python API** as the pybind11 target for the same headers: the same names, overloads with keyword arguments and default arguments, docstrings, aliases, containers, `std::function` wrappers and so on. Unlike pybind11, it has const classes, like the C# bindings (see [below](#const-classes-and-ownership)).

The extension builds against the CPython limited API (`Py_LIMITED_API`), so one binary serves every Python version. It doesn't depend on pybind11.

## Generating the C bindings

Pass `--output-desc-json c_desc.json` to the C generator. Also pass [`--copy-inherited-members`](/docs/generating_c.md#inherit-class-members) if you want, the copies of the inherited members are recognized and skipped (pybind11 binds them in the base classes only).

The description carries everything the Python generator needs from the parser: the field offsets (for `_offsetof_<field>`), the typedefs and the alternative type spellings (for the aliases), and which members were copied from bases.

## Running the generator

```sh
build/mrbind_gen_python \
    --input-json c_desc.json \
    --output-dir out \
    --module-name mylib \
    --module-qualname mypackage.mylib \
    --replace-namespace MyLib :: \
    --adjust-name '\bMyLib::' ''
```
Where:

* `--module-name` is the extension module name (`PyInit_<name>`), and `--module-qualname` is how it's imported, for the type names in the docstrings.

* `--replace-namespace A ::` puts the contents of `A` directly into the module, like `MB_PB11_STRIPPED_NAMESPACES` of the pybind11 target.

* `--adjust-name <regex> <replacement>` is applied to the C++ type names before making the Python names from them, like `MB_PB11_ADJUST_NAMES`. The pybind11 target names many types after their demangled `typeid()`, which is platform-specific. E.g. to match a Windows build, also pass `--adjust-name '\b(std::)?(size_t|uint64_t)\b' 'unsigned long long' --adjust-name '\b(std::)?(ptrdiff_t|int64_t)\b' 'long long' --adjust-name '(\w|>)\(' '$1 __cdecl('`.

* `--alias <alias> <target>` adds extra names, like `RegisterCustomAlias()` of the pybind11 target. Both are dotted paths in the module.

* `--extra-python <file.py>` embeds this Python code into the module and runs it in the module's namespace at the end of its initialization, for the functions written in C++ only for the pybind11 target. The code sees the module's names directly; don't import the module itself from it.

* `--ignore-for-python <regex>` skips the entities with matching C++ names, for the ones the pybind11 build ignores with annotations that the C bindings don't see.

* `--hide-field <name>` skips the fields with this name, e.g. the ones that are public only for the C bindings.

* `--iterate-by-index <regex>` gives the matching classes `__iter__` over `[0, elements)` with `operator[]`, for the free `begin()`/`end()` templates that the C bindings don't instantiate.

* `--ignore-c-file <regex>` skips the entities from the matching C headers (relative to the include directory, without the extension), e.g. `^MyLibCuda/` to leave out a sub-library.

* `--release-gil` releases the GIL around every call into C++. Without it, only the calls taking callables release it. Use it for a module whose functions wait for other threads that call into Python (or take the GIL themselves).

* `--depends-on <module qualname>` makes a module of a sub-library: generate it from the same description with `--ignore-c-file` skipping all but its C headers, e.g. `--ignore-c-file '^(?!MyLibCuda/)' --depends-on mypackage.mylib`. It then uses the classes and enums of that module (imported first) instead of skipping them, and shares its runtime state. Both must be generated by the same `mrbind_gen_python`.

* `--adjust-typeid-name <regex> <replacement>` is applied to the C++ names before spelling them like `typeid()` does, e.g. `--adjust-typeid-name '(^|[^:\w])expected<' '$1tl::expected<'` if the C bindings were generated with `--merge-std-and-tl-expected`.
* `--adjust-alias-name <regex> <replacement>` is applied to the alias spellings after `--adjust-name`, for the spellings that the pybind11 target keeps as written (e.g. `std::vector<size_t>` while `--adjust-name` makes the rest canonical).

* `--adjust-doc-name <regex> <replacement>` is applied to the C++ names in the docs (`Generated from:`), e.g. to spell `size_t` as its underlying type if the pybind11 build was parsed without the `size_t` support.

* `--fragments <N>` splits the module into `N` source files, `<module>.cpp` and `<module>_1.cpp` to `<module>_<N-1>.cpp`, with a common header `<module>.h`, to compile them in parallel. A big module compiles slowly as one translation unit.

The output is `out/<module>.cpp` (and the other fragments) and `out/mrbind_py_runtime.h`. Compile the `.cpp` files as C++20 with `-DPy_LIMITED_API=0x03080000` (or newer), the Python headers, the C bindings headers, and link them to the C bindings library and `python3` (`python3.lib` on Windows; nothing on Linux and macOS).

The extension and the C bindings must use the same C++ standard library, because `__repr__` and the stream parameters pass `std::ostream`/`std::istream` objects created on the extension side.

## Extension modules in C++

The generated module exports a C++ interop API (see [`include/mrbind/python_over_c/cpp_api.h`](/include/mrbind/python_over_c/cpp_api.h)) in the capsule `<module qualname>.__mrbind_cpp_api__`: other extension modules can accept its objects as C++ objects, and return C++ objects as its objects, by the C++ type names of the bindings (e.g. `MR::Mesh`).

For pybind11 modules, [`include/mrbind/python_over_c/pybind11_casters.h`](/include/mrbind/python_over_c/pybind11_casters.h) has the type casters:
```cpp
#define MRBIND_PY_CPP_API_CAPSULE "mypackage.mylib.__mrbind_cpp_api__"
#include <mrbind/python_over_c/pybind11_casters.h>

MRBIND_PY_FOREIGN_TYPE(MyLib::Mesh, "MyLib::Mesh", "mypackage.mylib.Mesh")
```
Then the pybind11 functions can take and return `MyLib::Mesh` by value, reference, pointer, `std::shared_ptr` and `std::shared_ptr<const ...>`. Such a module must use the same C++ standard library as the C bindings.

The casters keep the [const classes](#const-classes-and-ownership): a returned const reference or pointer (or `std::shared_ptr<const T>`) is a `ConstT`, and a non-const reference or pointer parameter raises `TypeError` for a `ConstT` (a `std::shared_ptr<T>` parameter doesn't match it, so pybind11 tries the other overloads). The parameters by value (and `T &&`, which pybind11 can't tell from them) take a copy. Version 2 of the interop API (`wrap_ex()`, `wrap_shared_ex()`, `is_mutable()`) provides this.

## Comparing with the pybind11 bindings

[`scripts/python_api_dump.py`](/scripts/python_api_dump.py) dumps everything observable about a module (names, signatures, docstrings, properties, enum members) and diffs two dumps:
```sh
python3 scripts/python_api_dump.py dump mypackage.mylib --strip mypackage.mylib. -o old.json
python3 scripts/python_api_dump.py dump mypackage.mylib --path new_build --strip mypackage.mylib. -o new.json
python3 scripts/python_api_dump.py diff old.json new.json
```

## Const classes and ownership

Like in C#, every class `T` has two Python classes: `ConstT` with only the const members, and `T` with all of them. The names starting with a lowercase letter or `_` get `Const_` (`Const_std_vector_int`). `T` derives from `ConstT`, so:

* A mutable object is also a const one (`isinstance(T(), ConstT)`), but not the other way around.
* `ConstT` derives from the `Const...` classes of the bases, and `T` derives from `ConstT` and the mutable bases. So a mutable object is also a const or mutable base, and a const object is only a const base.
* A const method (also `__eq__`, `__len__`, `__iter__` and the other read-only container methods) is in `ConstT`. A non-const one is in `T`. If a name has both kinds of overloads, `T` has all of them, the non-const ones first.
* A field is a read-only property of `ConstT` (with the const getter), and a property of `T` with the mutable getter and the setter.
* The constructors are in `T`. `ConstT(...)` constructs a `T` and takes it over. The static members are in `ConstT` (and inherited by `T`).
* A parameter by value or by const reference or pointer takes both kinds of objects. A non-const reference or pointer only takes a mutable object, and then there are no implicit conversions (a temporary can't bind to it).
* The aliases of the classes get `Const...` aliases too, e.g. `ConstVertCoords` for `VertCoords`.

An object either owns its C++ object or references one, which is `_is_owning` (like `_IsOwning` in C#). A function returning a reference doesn't copy the referenced object (unlike pybind11, which copies the const references): it returns a non-owning object, of `ConstT` for a const reference or pointer and of `T` for a non-const one. It keeps alive the object it was obtained from (`self` for the methods), but like a C++ reference it sees the later modifications of that object. To keep a snapshot, copy it: `T(x)`. A result by value is an owning `T`.

The other objects that a C++ object references are kept alive by its Python object, from the lifetimes of the C description (like `MB_PB11_USE_PARSED_LIFETIMES` in pybind11, plus what C# does with them): the keyed ones are released when the C++ object drops them, e.g. assigning a pointer field releases the previous target, and a copy (or an assignment) keeps alive what its source keeps alive, but not the source itself.

## Deliberate differences from pybind11

* The const classes and the references to the C++ objects, see above.

The pybind11 target has a few naming bugs that this generator doesn't copy:

* The assignments (`operator=`) are `assign(self, other)`, not `operator`. There is one overload for the copy and the move assignment, since they are the same in Python.
* `*=` is `__imul__`, not `__imatmul__` (which is `@=`).
* `<`, `>`, `<=`, `>=` are `__lt__`, `__gt__`, `__le__`, `__ge__`, not `operator`, so the Python operators and `sorted()` work. The reflected ones are their mirrors (`x < y` is `y > x`).
* The prefix `++` and `--` are `increment()` and `decrement()`, not `operator` and `operator_minus_minus`. The postfix ones aren't bound: Python has no such operators, and they modify the object the same way.

## Known differences from pybind11

* Calling an unbound method with a wrong `self` raises CPython's own `TypeError` text.
* The iterators are lists built eagerly.
* Default arguments that aren't a number, `true`/`false`, a character or a string literal are printed as spelled in C++, in quotes (pybind11 prints the `repr()` of their value, e.g. of `std::numeric_limits<float>::max()`).
* The containers have the comparison methods (`__eq__`, `__contains__`, `count()`, `remove()`) if their elements are scalars, strings, pointers, enums, standard containers or wrappers of such, or classes with an `operator==` (or a base with one) in the C bindings. pybind11 checks `std::equality_comparable` instead, which is also true for a free `operator==` template that the C bindings don't instantiate, and for a comparison through a conversion operator (e.g. to `bool`).
* The docstrings come from the comments in the C bindings without the comment markers, which drops the empty lines in the middle of the comments.
* The overloads of the free functions are in the order of the C bindings (grouped by header), which can differ from the registration order of the pybind11 build.
* The offset of a reference field (`_offsetof_<field>`) is that of the next non-reference field minus the pointer sizes, if the parser's target platform has another pointer size (the other offsets are computed on this one). Without such a next field there is none.
* The sets have no `erase()` in the C bindings, so `discard()`, `remove()` and `pop()` rebuild the set. `pop()` returns the removed element.
* The empty tag types (e.g. `std::monostate`, a `std::greater<T>` comparator) are classes without constructors, like in pybind11. The C bindings don't take them, so a parameter of such type is only checked.
* `expected<T, E>` is a class (with `__bool__()`, `value()` and `error()`) only as the element of a `std::vector`. Elsewhere a returned one is unwrapped into the value, or raises its error. It has no `make_unexpected()`, the C bindings can't make one in the error state.
* A `std::function` returning `expected<T, E>` can hold a Python function (pybind11 can't).
* The abstract classes have no `assign()`, the C bindings don't assign them.
* The methods that `using Base::f;` brings into a class are bound on it too (the fields aren't, like in pybind11): the description can't tell them from the methods hiding those of the base.
* A `std::optional` without a class in the C bindings (e.g. only a parameter) has no Python class, its parameters take the value or `None`.
* The description is parsed for one platform, so a class that is declared differently per platform (e.g. under `#if defined(__x86_64__)`) has the members of that platform's declaration.
* The types and functions that aren't in the C bindings (e.g. the namespaces without bound entities, some template instantiations) aren't in the module either.
* A C++ extension module that uses `pybind11_casters.h` returns the `std::vector`s that have no class in the C bindings (no C function takes or returns them) as Python lists.
